## Scope and validation

Birth-name order must be supplied explicitly, because changing from given/middle/family to family/middle/given changes endpoint letters even though sums stay identical. Character normalization and the SDK's existing configured Y classification are reused. The sources do not specify every language's Y pronunciation; the SDK labels its spelling heuristic and supports explicit vowel/consonant selection.

These additions apply only when requested through `extensions.nameChallenges` on `name`/`profile` or through the new standalone Rust helper. Nicknames can be supplied independently. Existing multi-name collections and group calculations are preserved and are not automatically relabeled as birth-name challenges. No source text or report interpretation is bundled.

Tests cover published worked examples, zero and missing classes, a single matching letter, both orders, normalization/Y modes, master-switch independence, current-name isolation, coexistence with profile name sets, strict settings validation, old result equivalence and an exhaustive same-class endpoint table. Native consumers compare the same wire cases; fixtures generated by the CLI check binding agreement, while independent Rust examples check arithmetic.
